# Live Recording UI — Phase 1 Implementation Spec

**Status:** Approved 2026-09-22 · Companion to `docs/LIVE_RECORDING_DESIGN.md` (Phase 1). The implementing session is an Opus ultracode run; every step below names real files, real export names, real status strings, and the pitfalls verified against this repo on 2026-09-22.

## Context

Phase 0 (PR #36, commit 464ee52) shipped the whole server side of in-browser live recording per `docs/LIVE_RECORDING_DESIGN.md`: the `recordings` / `recording_segments` / `recording_parts` tables, the capture API under `/api/recordings/*` plus `POST /api/sessions/[id]/recording`, and the `finalize_recording` pipeline job. The "fake-recorder E2E" the Phase 0 commit mentions was an ad-hoc local script and is NOT checked in — nothing under `tests/` exercises recording beyond 401 probes.

There is no UI. Nothing can start a recording, upload parts, show the safety indicator, or offer the recovery card. The client also has no way to learn a session's recording id or status: neither `GET /api/sessions` nor `GET /api/sessions/[id]` includes the `recording` relation.

Phase 1 = the recorder engine in the browser, the pages around it, the session-detail integration, and the small backend additions the UI needs. The session-status vocabulary (`src/lib/session-status.ts`) stays untouched: a session is `draft` while its `Recording` row tracks capture. The governing invariant: **captured audio must never be lost** — audio leaves the tab continuously, un-uploaded audio lives in IndexedDB, interruption is a recoverable state, not an error.

## Decisions (made with the user, 2026-09-22)

| 8 | Rotation ~10 min at silence (rolling RMS), 15 min hard cap; pause > 30 min closes the segment. |

| 10 | Opening `/sessions/[id]/record` while the recording is live elsewhere (fresh heartbeat, no local tail): show **"active in another tab" with an explicit Take over button**. Never auto-POST takeover on mount. |
| 11 | **One-click Stop**, no confirm. |
| 12 | **`NEXT_PUBLIC_RECORDING_PART_MAX_MS`** (and `NEXT_PUBLIC_RECORDING_ROTATION_MS`) compile-time knobs in `constants.ts`; Playwright `webServer.env` sets the part cap to 5000 so a 20 s run lands parts mid-recording. |

Smaller calls made in this spec (change if you disagree): chunks are stored in IndexedDB as the MediaRecorder `Blob` itself (structured-cloneable in every target browser and in Node 18+ / fake-indexeddb), with `seq` assigned and the put issued synchronously in `ondataavailable` — no `await` before the write; crash drain reuses the token persisted in IDB and never auto-takes-over; a Web Lock held by the live recorder keeps a second same-browser tab from draining; after Stop the tail upload retries forever while offline, with a "Finalize without the un-uploaded tail" escape after 60 s that warns the tail is then unrecoverable; permanently rejected parts (400/413) are dropped from the queue, kept in IDB, and surface as `degraded`; session-list / dashboard badges are included; a `failed` recording offers only Retry-assembly / Discard (the server refuses takeover from `failed`).

## Verified backend contract (client must branch on exactly these)

Common: middleware 401s `/api/*` without a JWT; route-level `requireAuth` → 401 `{ error: 'Authentication required' }`; ownership failures → 404. Capture routes check in this order: owner (404) → `x-recorder-token` (409) → recording status (409) → validation (400) → business rule. Server constants (`src/services/recording.ts`): `RECORDING_STALE_SECONDS = 180`, `MAX_PART_BYTES = 8 MiB`, `MAX_RECORDING_BYTES = 1 GiB`, `RECORDING_BITS_PER_SECOND = 48_000`. `RecordingDisplayStatus = 'recording'|'paused'|'interrupted'|'finalizing'|'finalized'|'failed'` (`interrupted` is derived server-side from heartbeat age vs DB `NOW()`; never compute it client-side).

| Call | 2xx | Errors (`error` string; `code` is added in Step 1) |
|---|---|---|
| `POST /api/sessions` `{ campaign_id, title, session_date }` (plain auth, unlimited) | **201** raw `GamingSession` (`id`, `status:'draft'`) | 400 `Validation error`; 404 `Campaign not found` |
| `POST /api/sessions/[id]/recording` `{ mimeType? }` — start AND takeover; rotates the token; forces status `recording` | `{ recording: RecordingState, recorderToken, nextSegmentIndex }` | 404; 409 `Session already has audio attached`; 409 `Recording is already being finalized` (status ∉ recording/paused — includes `failed`); 429 `Too many authentication attempts` + `Retry-After` |
| `GET /api/recordings/[id]` (auth only, no limiter) | `{ recording: RecordingState }` | 404 |
| `DELETE /api/recordings/[id]` (auth only) | `{ message: 'Recording discarded' }` | 409 `Recording has been finalized and can no longer be discarded` (finalizing/finalized) |
| `POST /api/recordings/[id]/segments` `{ index }` (token) | `{ segment: { index, status } }` idempotent | 409 `Recording was taken over in another tab`; 409 `Recording is not capturing`; 409 `Segment index out of order` |
| `PUT .../segments/[n]/parts/[m]` raw bytes, `Content-Type: application/octet-stream` (token; accepted while `paused`; implicit heartbeat) | `{ received: n }` idempotent upsert | 409 taken-over; 409 `Recording is not capturing`; 400 `Invalid segment or part index`; 404 `Segment not found`; 409 `Segment is closed`; 400 `Empty part`; 413 `Part exceeds maximum size`; 413 `Recording exceeds maximum total size` |
| `POST .../segments/[n]/close` `{ partCount ≥ 1 }` (token; no status check; no heartbeat) | `{ segment: { index, status:'closed' } }` (200 also when already closed, before body parse) | 409 taken-over; 404 `Segment not found`; **409 `{ error: 'Parts missing from segment', missing: number[] }`** |
| `PUT .../heartbeat` `{ state: 'recording'\|'paused' }` (token) — **the only way pause/resume reaches the server** (writes `status = state`) | `{ received: true }` | 409 taken-over; 409 `Recording is not capturing` |
| `POST /api/recordings/[id]/finalize` (auth only, NO token) | `{ status: 'finalizing', jobId }` | 409 `Recording is already finalizing or finalized`; **400 `No audio was captured — nothing to finalize`** (zero part rows) |
| `GET /api/sessions/[id]/progress` | `{ status, …, job: { id, status, step, attempts, maxAttempts, nextRunAt, lastError } \| null }` (`job` = latest job of ANY type) | |

`RecordingState` = `{ id, sessionId, status, mimeType, startedAt, lastHeartbeatAt, totalBytes, estimatedDurationSeconds, segmentCount, finalizedUploadId, errorMessage }`. After finalize, parts are deleted so `totalBytes` reads 0; `segmentCount` survives; the `Recording` row persists forever as `finalized`.

Facts that drive the client algorithms: `openSegment` is idempotent and gapless (`index === last+1`); a crashed segment stays `open` forever; `runFinalizeRecordingStep` assembles every segment from `contiguousParts` regardless of `status` (closing is an integrity check, never a prerequisite); an empty segment is skipped by finalize and CANNOT be closed (`partCount` min 1); `beginFinalize` accepts `recording|paused|failed`. Post-Stop write order on the worker: `Upload` row → `recording.finalizedUploadId` → session `uploaded` (`linkSessionToUpload`) → recording `finalized` → parts deleted → `completeJob` → if `enqueueProcessing` (`!isTestAccount(email) || isAiMocked()`): `enqueueProcessSession` + session `transcribing`. So the client can see `(uploaded, finalizing)` for milliseconds but never `(draft, finalized)`. Worker poll interval `PIPELINE_POLL_INTERVAL_MS` default 5000.

Rate limits are per **minute** (`src/lib/rate-limiter.ts`), not per 15 minutes as `auth-utils.ts` JSDoc and the design doc say: `authRateLimiter` = 10/min prod, 100/min when `NODE_ENV=development` or `CI=true`, keyed per user, shared with `/api/billing/checkout`. Only `POST /recording` is limited; everything else recording-related is plain `requireAuth`.

## Step 1 — Backend additions (all in files Phase 0 touched)

### 1a. Recording summary on session reads (hard prerequisite for every banner/card)
- `src/services/recording.ts`: add
  ```ts
  export interface RecordingSummary { id; status: RecordingDisplayStatus; estimatedDurationSeconds; startedAt: Date; lastHeartbeatAt: Date; errorMessage: string|null }
  export const recordingSummarySelect = { select: { id:true, status:true, startedAt:true, lastHeartbeatAt:true, errorMessage:true, segments: { select: { sizeBytes:true } } } } as const;  // NEVER recorderToken
  export type RecordingSummaryRow = { id; status; startedAt; lastHeartbeatAt; errorMessage; segments: { sizeBytes:number }[] };
  export async function dbNowMs(): Promise<number>  // SELECT NOW() as now — same pattern as getRecordingState
  export function summarizeRecording(row: RecordingSummaryRow, nowMs: number): RecordingSummary  // status = deriveDisplayStatus(row.status, row.lastHeartbeatAt, nowMs); duration = estimateDurationSeconds(Σ segments.sizeBytes)
  ```
  `RecordingSegment.sizeBytes` is kept equal to the sum of its parts by `savePart` and survives finalize, so it is the cheap list-level source — never aggregate `recording_parts` per row.
- `src/services/database.ts`: add `recording: recordingSummarySelect` to the `include` of both `getSessions` and `getSessionById`; extend `SessionListItem` and `SessionWithIncludes` with `recording: RecordingSummaryRow | null`. (Additive; `requireSessionOwner` consumers are unaffected. Any test that mocks `getSessionById` with a fixed shape needs `recording: null` to type-check.)
- `src/app/api/sessions/route.ts` GET: `const nowMs = sessions.some(s => s.recording) ? await dbNowMs() : 0;` then map each row with `recording: s.recording ? summarizeRecording(s.recording, nowMs) : null` **set AFTER the spread** so the raw relation (with `segments[]`) never leaks. One `SELECT NOW()` per request, never per row.
- `src/app/api/sessions/[id]/route.ts` GET: same, `recording: session.recording ? summarizeRecording(session.recording, await dbNowMs()) : null` after the spread.
- Do NOT add recording data to `/api/sessions/[id]/progress` (hot path, select-only by design); the record page polls `GET /api/recordings/[id]` instead.
- Client types: create `src/lib/recording/types.ts` (browser-safe, no server imports) with `RecordingDisplayStatus`, `RecordingSummary` (dates as ISO strings), `RecordingState`, `StartRecordingResponse`; add `recording: RecordingSummary | null` to `SessionDetail` in `src/app/sessions/[id]/types.ts` and to the local `Session` interfaces in `src/app/sessions/page.tsx`, `src/components/Dashboard.tsx`, `src/app/campaigns/[id]/page.tsx`.
- Vitest: extend `src/services/__tests__/recording.test.ts` with `summarizeRecording` cases (sums segment bytes; derives `interrupted` when heartbeat > 180 s before `nowMs`; passes terminal statuses through; empty segments → 0).

### 1b. Stable `code` on every recording 4xx (the client must never match on message text)
- `src/lib/route-utils.ts`: add `recordingError(status, code, message, extra?)` → `NextResponse.json({ error: message, code, ...extra }, { status })` and make `requireRecorderToken` use it with `code: 'stale_token'`.
- Codes: `stale_token` (409 taken over), `not_capturing` (409), `segment_gap` (409 index out of order), `segment_not_found` (404), `segment_closed` (409), `parts_missing` (409, keeps `missing[]`), `empty_part` (400), `invalid_request` (400), `part_too_large` (413), `recording_too_large` (413), `already_finalizing` (409 from finalize), `nothing_captured` (400 from finalize), `cannot_discard` (409 from DELETE), `has_audio` / `past_capture` (409s from POST /recording), `still_capturing` (new, 1d). Keep the existing `error` strings unchanged (tests assert them).
- Route-protection tests keep passing (they assert 401 only).

### 1c. Race guards (a concurrent Finalize + Resume can currently flip a finalizing recording back to `recording`)
- `beginFinalize`: replace the unconditional update with `prisma.recording.updateMany({ where: { id, status: { in: ['recording','paused','failed'] } }, data: { status:'finalizing', errorMessage:null } })` → `'conflict'` when `count === 0` (keep the part-count `'empty'` check before it).
- `startOrTakeoverRecording`: first statement inside the transaction: `await tx.$queryRaw\`SELECT id FROM gaming_sessions WHERE id = ${sessionId} FOR UPDATE\`` (precedent: `src/services/pipeline/queue.ts:40`). Locking the parent session row serializes takeover, finalize, and the concurrent-first-start create path (which otherwise races into P2002 on `recordings.session_id`). Then update the recording row (token, status, mimeType) BEFORE reading segments, and compute `nextSegmentIndex` from a fresh `tx.recordingSegment.findFirst({ orderBy: { index: 'desc' } })` after that write. Today the segment read happens before the row lock, so an old tab's `openSegment` can commit segment N+1 in between and the takeover still returns N+1.
- Token check inside every capture write (the route-entry checks are time-of-check/time-of-use): add `assertCapturing(tx, recordingId, token)` = `UPDATE recordings SET last_heartbeat_at = NOW(), updated_at = NOW() WHERE id = ${recordingId} AND recorder_token = ${token} AND status IN ('recording','paused') RETURNING status`; zero rows → throw `CaptureRejectedError` (route maps to 409 `stale_token` or `not_capturing` by re-reading the row). Call it as the FIRST statement inside the transactions of `savePart`, `openSegment` and `closeSegment`; add `AND recorder_token = ${token}` to `heartbeatRecording`'s UPDATE. Signatures gain a `token` argument; routes pass `request.headers.get('x-recorder-token')`. This replaces the trailing unguarded `touchHeartbeat` in `savePart`. On rejection in `savePart`, best-effort `deleteObjectByKey(storageKey)` for the object written just before the transaction (the client keeps its IDB copy because it saw a 409, not a 200).
- `GET /api/recordings/[id]` (`getRecordingState`): add `segments: Array<{ index, status: 'open'|'closed', partCount, maxPartIndex: number|null, sizeBytes }>` from one `recordingSegment.findMany({ where: { recordingId }, orderBy: { index: 'asc' }, include: { parts: { select: { index: true } } } })`. Compute `partCount` and `maxPartIndex` from the parts array, not the stored column, which diverges when there is a gap. The drain needs this: ACKed rows were already deleted from IDB, so IDB alone cannot say what the server holds.
- `runFinalizeRecordingStep`: after the `findUnique`, throw `PermanentJobError('Recording is no longer finalizing')` unless `recording.status === 'finalizing' || recording.finalizedUploadId`. In `finishBookkeeping` change the `'finalized'` write to `updateMany({ where: { id, status: 'finalizing' } })` and delete only the part ids actually assembled (loaded at the top of the step), not a fresh query of all parts.

### 1d. `still_capturing` guard on finalize / takeover / discard (a recovery card in tab B must not strand tab A)
- `POST /api/recordings/[id]/finalize`: accept optional JSON body `{ force?: boolean }` (`request.json().catch(() => ({}))`) and read `x-recorder-token` directly (do not use `requireRecorderToken`, it hard-409s on a missing header). `const state = await getRecordingState(recording); if ((state.status === 'recording' || state.status === 'paused') && token !== recording.recorderToken && !force) return recordingError(409, 'still_capturing', 'Recording is still capturing', { lastHeartbeatAt: state.lastHeartbeatAt })`. Derived `interrupted` (stale > 180 s) needs no force. The Stop path always sends the token; the recovery card sends `force: true` only after a confirm that shows heartbeat age.
- `POST /api/sessions/[id]/recording`: add `force?: boolean` to `startRecordingSchema`; when an existing recording's derived status is `recording`/`paused` and `!force` → 409 `still_capturing`. Also 409 `past_capture` when `session.transcriptions.length > 0` or `getLatestJob(id)` is pending/running (closes the "draft with transcriptions" hole where finalize would return the wrong job).
- `DELETE /api/recordings/[id]`: same `still_capturing` guard with `?force=1` or body `{ force }` — discard is worse than finalize (the live tab's PUTs start 404ing).
- `POST /api/sessions/[id]/upload`: 409 `{ error: 'Session has a live recording in progress' }` when a `Recording` row exists with status not `finalized`.
- Finalize route: if `enqueueFinalizeRecording` returns a job whose `type !== 'finalize_recording'`, revert the status and 409 — never report `finalizing` without a finalize job.

### 1e. Worker / progress
- `reapStaleJobs` (`queue.ts`): `RETURNING session_id, type`; in `workerLoop` call `markRecordingFailed(sessionId, msg)` when `type === 'finalize_recording'` (session stays `draft`), else `db.setSessionError` as today. Vitest the branch.
- `beginFinalize`: also accept status `finalizing` when `getLatestJob(sessionId)` is not pending/running (re-enqueue), so `finalizing` is never terminal without a job.
- `DELETE /api/transcription/[sessionId]` (Cancel): refuse with 409 when the session is `draft` / the active job is `finalize_recording` (today it would cancel the finalize job and set the session `uploaded` with no `uploadId`).
- `GET /api/sessions/[id]/progress`: add `type: job.type` to the `job` object (the client uses it to tell "finalize completed, process not yet enqueued" from "process pending").
- Fix the JSDoc in `src/lib/auth-utils.ts` ("per 15 minutes" → "per minute; 100/min in dev/CI") and the same note in root `CLAUDE.md` / `src/app/api/CLAUDE.md`.
- Optional: `DELETE /api/sessions/[id]` calls `discardRecording` first when a non-finalized recording exists, so part objects are not orphaned by the cascade.

### 1f. Finalize assembly fixes (`src/services/pipeline/steps/finalizeRecording.ts`)
- **Always remux, even for one segment.** Today a single segment is published as-is. MediaRecorder WebM has no Duration or Cues, so `probeAudioDurationSeconds` returns null (it has NO decode fallback, contrary to the design doc) and the file is not seekable in the audio player. Single segment: `ffmpeg -y -i <seg> -map 0:a -c copy <workDir>/assembled.webm` (new path, never in place). Multiple segments: the existing concat plus `-map 0:a -avoid_negative_ts make_zero`.
- Duration fallback: when `probeAudioDurationSeconds` returns null, try `getAudioDuration(assembledPath)` (it decodes; returns fractional seconds and rejects on failure, so wrap it and round).
- Channel/sample-rate guard before a multi-segment concat: ffprobe each segment for `codec_name,channels,sample_rate`; if they all match, stream copy; otherwise re-encode with `-filter_complex concat=n=N:v=0:a=1 -ac 1 -c:a libopus -b:a 48k`. `channelCount: 1` in getUserMedia is only a hint, and a mic swap mid-session can change it. Vitest the decision function.
- Consequence: finalize now always needs system ffmpeg, so `pull-request.yml`'s `test` job needs `sudo apt-get update && sudo apt-get install -y ffmpeg` before `npm run test:ci`. Per LESSONS.md, Claude's tokens lack the `workflows` permission, so this hunk may have to be applied by hand — flag it in the PR description. The E2E asserts `session.duration > 0`.

### IndexedDB schema (`rpg-session-recorder`, v1)
- Store `recordings`, keyPath `recordingId`: `{ recordingId, sessionId, userId, recorderToken, mimeType, createdAt, updatedAt }`; index `bySession` (unique). Put at `start()` and at takeover (overwrite `recorderToken` whenever POST `/recording` returns a new one — the persisted token is what makes a non-destructive crash drain possible); deleted when finalized (poll saw `finalized`) or discarded.
- Store `chunks`, keyPath `['recordingId','segmentIndex','seq']` (array keys compare element-wise → primary-key range = capture order): `{ recordingId, segmentIndex, seq, partIndex, blob: Blob, size, durationMs, capturedAt }`; indexes `byRecording` (`recordingId`), `byPart` (`['recordingId','segmentIndex','partIndex']`). The PUT body is `new Blob(rows.map(r => r.blob), { type: mimeType })` — no `arrayBuffer()` anywhere on the write path. Use `{ durability: 'strict' }` on readwrite transactions (Chrome defaults to relaxed; ignored where unsupported).
- Invariants: **I1** a `chunks` row exists ⇔ its bytes are not yet ACKed (2xx on PUT only — a PUT of a part the ledger already holds answers 2xx even after close, so `segment_closed` means the part is NOT there and is never an ACK); the put is issued synchronously in `ondataavailable` and the assembler only sees the chunk after the transaction's `complete` event; all rows of a part deleted in ONE transaction only after ACK. **I2** `seq` strictly increasing per `(recording, segment)`, assigned synchronously as the first statement of the handler; `partIndex` non-decreasing in `seq`, contiguous per part. **I4** the queue is FIFO, so a segment's un-ACKed parts are always a suffix → `max(pending partIndex) + 1` is its true `partCount` (used by the drain's close). **I5** segment indexes are assigned locally and contiguously; `startSegment(n)` enqueues a non-blocking `{ kind:'open', n }` job IMMEDIATELY (eager, FIFO), even if the segment later ends empty. Lazy open-at-first-part breaks the server's gapless rule when a segment produces nothing (mic lost right after rotation: the next open would 409 `segment_gap`); a blocking POST before starting the recorder stalls rotation while offline. An opened-but-empty segment is never closed, and finalize skips it. IDB may still hold chunks for segments whose open never reached the server; the drain opens every missing index ascending. Size: ~60 KB per 10 s chunk; a fully offline 5 h session ≈ 1800 rows / 108 MB; `navigator.storage.persist()` requested best-effort at start.

### Upload queue error policy (per `code`)
`network` / 5xx / 429 (honor `Retry-After`) → retry with backoff at the head; `navigator.onLine === false` → wait for `online` or a 30 s fallback, no timer spin. `401` → `auth-expired` health, pause the queue (keep recording + IDB writes), retry on the next tick — never terminal. `stale_token` → **terminal**: stop capture hardware, keep IDB, phase `taken-over`. `not_capturing` → terminal "finalized elsewhere" (only if the request's generation is current; stale post-Stop heartbeats are ignored). `recording_not_found` (404 on the recording) → terminal (session deleted). `segment_not_found` → insert `{ kind:'open', segmentIndex }` at the head and retry (recoverable after a crash where the open never landed). `segment_gap` → fatal client bug: surface loudly, capture continues, IDB retained. `segment_closed` on a part → the part is not in the ledger and can no longer be written: it becomes **unresolved** like a refused part (rows kept; never an ACK). `parts_missing` on close → engine re-PUTs exactly `missing[]` from IDB (`enqueueFront`) once — skipping parts already unresolved — then re-closes; on a second `parts_missing` it closes as the contiguous prefix ONLY when every missing part is gone locally too. A segment with an unresolved part is never closed (not even as a prefix, which would make a later Retry hit `segment_closed`): its close is deferred until Retry lands the part, and dropped if the user accepts the loss (finalize assembles the open segment's contiguous prefix). `empty_part` / `invalid_request` / `part_too_large` → client bug: take the job off the queue (never retry a 4xx forever) but keep it **unresolved** — its rows stay in IndexedDB, health stays `degraded` until it is retried successfully or explicitly abandoned (a later success must not clear it), and "saved through" only advances across a CONTIGUOUS acknowledged prefix (a refused part freezes it at that part's start). Stop never finalizes across an unresolved part: after the drain it parks in phase `tail-blocked` (Retry upload / Finalize without it — confirmed / Discard). The crash drain reports refused parts as `recovery.unresolvedSeconds`, and the recovery card confirms before finalizing across them. Resume does not resolve them: the takeover drain's still-refused parts (and the closes they hold back) are carried into the live queue, so a later Stop parks in `tail-blocked` instead of finalizing and purging them. `recording_too_large` → stop capture and offer Finalize.

### Oversized blobs → bounded parts
A delayed `dataavailable` (after a long suspension or screen lock) can carry far more than one timeslice. Whole-blob grouping would then produce a part over the server's 8 MiB cap — permanently refused, and a gap that invalidates the rest of the segment. So `onChunk` first splits any blob larger than `PART_MAX_BYTES` (3 MiB) into consecutive byte ranges of at most `PART_MAX_BYTES` (`Blob.slice`: synchronous, copy-free); each range becomes its own chunk row with its own `seq`, a proportional share of the duration, and its part index stamped at write time (retry identity: a retry re-sends the same rows). Because a part seals once it reaches `PART_MAX_BYTES`, the largest possible part is < 2 × `PART_MAX_BYTES` = 6 MiB, under the server cap. Concatenation order is preserved (seq order = byte order). Tested with a single 7 MiB blob.

### Backoff/heartbeat/rotation timing notes
Chunk `durationMs = clamp(capturedAt − run.lastBlobAt, 0, TIMESLICE_MS + 500)`; MediaRecorder blobs carry no duration and `BlobEvent.timecode` is unreliable, so "saved through" is wall-clock approximate (±1 timeslice) by design; the recovery card uses the server's byte-based estimate. RMS is sampled with `setInterval(100)` (never rAF — paused in hidden tabs); when hidden it degrades to ~1 Hz, which only delays rotation toward the hard cap; rotation due-ness is computed from `now − segmentStartedAt` on every tick / `ondataavailable` / `visibilitychange`, never from a counted timer. Chromium's fake mic emits periodic beeps over silence, so silence-based rotation never fires in CI (fine: rotation is unit-tested).

## Step 3 — Engine orchestrator + React binding

`src/lib/recording/engine.ts` — `class RecorderEngine` lives OUTSIDE React (registry), owns stream / meter / `SegmentRun`s / store / queue / heartbeat / wake lock, exposes `subscribe` / `getSnapshot` for `useSyncExternalStore` and imperative commands. **Every command is phase-guarded and idempotent** (double click, StrictMode double effects). Transitions (pause / resume / rotate / stop) are serialized through a promise chain `op = op.then(fn, fn).catch(log)`; a queued rotation re-checks `phase === 'recording' && !stopRequested` at execution time and becomes a no-op otherwise.

Phases: `idle → preflight → starting → recording ⇄ paused → stopping → uploading-tail → finalizing → finalized`; branches `finalize-failed` (Retry / Discard), `recovering → recovery-choice` (modes `tail | interrupted | live-elsewhere | failed`), `discarding → discarded`, terminal `taken-over`, `unsupported`, `error`. Sub-flags on the snapshot, not phases: `micLost`, `uploadHealth`, `wakeLockActive`, `level`.

Key flows (pseudo-code):

```
preflight(deviceId):  support gate → releaseStream → stream = acquireMicStream → devices = listAudioInputs → meter → RMS sampling → track.onended = onMicLost → phase PREFLIGHT_READY
  // Create the AudioContext only AFTER getUserMedia resolves: Chromium, WebKit and Gecko all exempt a page that is actively capturing from the autoplay gate, so the meter runs without a gesture (verified in browser source; the "suspended AudioContext" worry does not apply). StrictMode cleanup must still ctx.close().

start({ recordingId, recorderToken, nextSegmentIndex, mimeType }):   // ONLY from a click handler (Start / Resume / Take over)
  guard phase === 'preflight'; putMeta; storage.persist() best-effort; new UploadQueue + Heartbeat; requestWakeLock; install visibilitychange/online/devicechange listeners
  startSegment(nextSegmentIndex); heartbeat.start(() => phase==='paused' ? 'paused' : 'recording'); phase STARTED

onChunk(blob, capturedAt) for segment s (closure-bound):
  seq = assembler.nextSeq(s); partIndex = assembler.currentPartIndex(s)      // SYNCHRONOUS, first statements
  putDone = store.putChunk({ recordingId, s, seq, partIndex, blob, size: blob.size, durationMs, capturedAt })   // I1: request issued synchronously; IDB runs same-scope readwrite txs in creation order
  writeChain = writeChain.then(async () => {
    await putDone
    sealed = assembler.add(s, { seq, size, mediaEndMs }); elapsedMs = clock.activeMs()
    if (sealed) queue.enqueue({ kind:'part', ...sealed })   // the segment's open job was enqueued eagerly in startSegment
    heartbeat.poke(); maybeRotate(capturedAt)              // rotation + hard cap re-evaluated on every chunk: media events keep arriving in background tabs, timers don't
  }).catch(e => { memoryFallback.set(key, blob); set({ storageError: true }) })
  // IDB write failed (QuotaExceeded, UnknownError, closed connection): keep the blob in memory and STILL upload it — refusing to upload
  // un-persisted bytes would lose everything. Safety indicator switches to 'Not saving locally — keep this tab online'. Never swallow silently.
  // The queue's part job reads bytes from memoryFallback when the store has none.

finishSegment(s) (from onStopped via writeChain): sealed = assembler.flush(s) → enqueue part; n = assembler.partCount(s); if (n > 0) enqueue { kind:'close', s, partCount:n }   // NEVER close an empty segment (server min 1)

startSegment(n): run = createSegmentRun(stream, n, handlersFor(n)); run.start(TIMESLICE_MS); queue.enqueue({ kind:'open', segmentIndex: n }); nextSegmentIndex = n + 1
rotate(): next = createSegmentRun(stream, nextSegmentIndex, …); next.start(TIMESLICE_MS); enqueue open; old = run; run = next; void stopRun(old, 'rotate'); silence.reset()
  // Start the NEW recorder first, then stop the old one, in one synchronous block: several MediaRecorders on one MediaStream are allowed,
  // and a sub-second overlap (a few duplicated ms) beats any gap. Closure-bound handlers keep the old run's final blob on the old segment.
stopRun(run, reason): run.stopReason = reason (on THAT instance, never a shared field); register the 'stop' listener, then rec.stop();
  resolve only after 'stop' AND `await writeChain` (the tail chunk is persisted and the part flushed).
  An unexpected 'stop' or 'error' (all tracks ended, device unplugged) arrives with stopReason undefined → treat as 'device-lost':
  close the segment normally and enter micLost; never auto-finalize. Ignore events from recorder instances that are no longer current.
  Guard recorder calls by state: pause() only when 'recording', resume() only when 'paused', requestData()/stop() only when not 'inactive'.
pause(): additionally mark the current part flushOnNextBlob so the requestData() blob force-seals the open part — the audio before the break uploads during the break and the safety indicator catches up.
pause(): guard 'recording'; run.requestData(); run.pause(); pausedAt = now; arm PAUSE_CLOSES_SEGMENT_MS timer (also re-checked on heartbeat tick + visibilitychange because hidden timers throttle); phase PAUSE; heartbeat.markDirty()
long-pause close: r = run; run = null; void r.stop()   // phase stays paused, heartbeats continue with state 'paused'
resume(): guard 'paused'; if (run?.state==='paused') run.resume() else if (!micLost) startSegment(nextSegmentIndex); phase RESUME; heartbeat.markDirty()
onMicLost(): set micLost; if (run) { r = run; run = null; void stopRun(r, 'device-lost') }   // segment ends cleanly; phase unchanged; heartbeats continue with state 'paused' (so the server status is truthful); Pause is disabled; HUD shows MicLostBanner
switchMicrophone(id): new stream → stop old run → swap stream/meter → if phase==='recording' startSegment(next)   // paused: new segment starts on resume

stop():   // one click, no confirm
  guard 'recording'|'paused'; stopRequested = true; phase STOP; clear rotation/pause timers   // KEEP the heartbeat running through the drain
  if (run) { r = run; run = null; await r.stop() }   // recorder.stop() flushes the final dataavailable then onstop → finishSegment via writeChain
  await writeChain; releaseStream(); releaseWakeLock(); phase CAPTURE_STOPPED
  await queue.drained()            // retries forever while offline; HUD 'Uploading remaining audio… N parts left'; after 60 s degraded/offline show 'Finalize without the un-uploaded tail' → abandonTailAndFinalize() with an explicit warning
  heartbeat.stop(); generation++   // cancel heartbeat + bump generation immediately BEFORE the finalize POST
  phase TAIL_UPLOADED; await enqueueFinalizeAndPoll()

enqueueFinalizeAndPoll():
  try finalizeRecording(recordingId, { token })      // token proves we are the capturing tab (1d)
  catch: 409 already_finalizing → fall through to polling; 400 nothing_captured → phase finalize-failed with 'Nothing was recorded' + Discard only; network/5xx → sleep 2 s, retry
  loop every FINALIZE_POLL_MS: r = getRecording(recordingId) (network error → retry)
    'finalized' → store.deleteRecording; then poll GET /api/sessions/[id]/progress until status ∈ {transcribing, transcribed, summarizing, completed, error} OR (status==='uploaded' seen twice ≥3 s apart with job.type !== 'process_session' or job.status !== 'running') OR 5 s grace elapsed → set redirectTo `/sessions/${sessionId}?initialState=processing`
    'failed' → phase finalize-failed (errorMessage; Retry = POST finalize again — beginFinalize allows 'failed'; Discard allowed)
    'finalizing' → keep polling; optionally read /progress job.attempts > 1 to show 'Retrying (n/5)…' (transient finalize failures keep 'finalizing' for up to ~7.5 min with no error on the recording endpoint)
    404 → redirectTo '/sessions' (session deleted)

onFatalFromServer(kind):   // stale_token | not_capturing | recording_not_found, from queue OR heartbeat, current generation only
  stop hardware, queue.stop(), heartbeat.stop(), clear timers, release wake lock; phase TAKEN_OVER; IDB tail RETAINED
  message: stale_token → 'This recording was taken over in another tab. Recording here has stopped; everything already uploaded is safe.'; not_capturing → 'This recording was finalized elsewhere.'; plus 'About N min of audio from this tab could not be attached' from Σ pending bytes·8/48000 when > 0

bootstrap():   // idempotent (memoized promise) — the record page's mount effect calls this and nothing else; StrictMode-safe
  if (phase !== 'idle') return                      // engine already live (navigated from /sessions/record)
  info = getSessionRecording(sessionId); if (info.uploadId) → redirectTo `/sessions/${sessionId}`
  rec = info.recording; if (!rec) return             // fresh: page shows PreflightPanel; Start click → startOrTakeover → engine.start
  GC: for any IDB meta of THIS session whose recordingId ≠ rec.id (a discarded/re-recorded predecessor) → deleteRecording; also delete metas older than 30 days for this user
  'finalizing' → phase finalizing; enqueueFinalizeAndPoll() (409 tolerated → polls)
  'finalized' → redirectTo `/sessions/${sessionId}?initialState=processing`
  'failed' → recovery-choice mode 'failed' (Retry assembly / Discard only; takeover is refused server-side); pending IDB rows for it are unrecoverable → mention 'N s could not be recovered' and delete them
  // (a finalized recording's takeover 409 is has_audio 'Session already has audio attached' — the uploadId check runs first — not past_capture)
  Web Lock: the live recorder holds navigator.locks.request(`recorder:${recordingId}`) from start() until finalized/taken-over (auto-released on tab death).
  if the lock is HELD (query with { ifAvailable: true }) → recovery-choice mode 'live-elsewhere'; never drain, never POST (a second tab in the SAME browser shares IndexedDB and would otherwise upload the live tab's rows)
  pending = getPendingChunks(rec.id)
  'recording'|'paused' AND pending.length === 0 → recovery-choice mode 'live-elsewhere' (decision 10): copy 'Recording may be active in another tab, or this tab was reloaded'; [Take over in this tab] → takeover(force) after confirm showing heartbeat age; [Back to session]
  otherwise (a local tail exists and the lock is free, or 'interrupted') → drainTail(storedToken) → recovery-choice mode tail|interrupted

drainTail(token):   // EXACT algorithm — drain with the token PERSISTED in IDB meta; do NOT take over first.
  // Why: takeover rotates the token and forces status 'recording'; doing it just to drain would kill a recorder live on ANOTHER device, and a
  // non-rotating drain is non-destructive. A 409 stale_token is the positive signal that a takeover really happened elsewhere.
  server = getRecording(recordingId)                          // now includes segments[{ index, status, partCount, maxPartIndex }]
  status ∈ {finalizing, finalized, failed} or 404 (and meta.userId === current user) → rows can never be attached: show 'N s of audio from this tab could not be attached', delete rows, stop
  grouped = groupPending(getPendingChunks(recordingId))       // ascending (segment, part); cursor per part when reading bytes
  for each segment s ascending:
    // before the loop: enqueue { open, i } for EVERY i from server.segments.length (the server's next index) through max(local s), ascending —
    // including indexes with no local rows (an empty segment whose open never landed), otherwise the next open 409s segment_gap

    for each part p ascending: enqueue { part, s, p, ...meta }
    partCount = max(server maxPartIndex(s) + 1, max(local p) + 1)   // ACKed rows are gone from IDB, so the server ledger fills in
    if (partCount >= 1) enqueue { close, s, partCount }         // 409 parts_missing → re-PUT locally present indexes once, retry once, then stop (finalize assembles the contiguous prefix of an OPEN segment)
  await queue.drained()
  on stale_token → recovery-choice mode 'live-elsewhere' (the user decides whether to take over); on not_capturing → the 'could not be attached' notice
  // Drained PUTs refresh last_heartbeat_at (savePart is an implicit heartbeat), so the row reads as live for up to 180 s after a drain — benign.
  // Segments fully ACKed before the crash but never closed have no pending rows → left open on purpose.

takeover(force?):   // ONLY from the Take-over / Resume click; never from an effect
  resp = startOrTakeover(sessionId, meta.mimeType ?? RECORDING_MIME_TYPE, force)   // 409 still_capturing without force → confirm with heartbeat age; 429 → 'Please wait N s' from Retry-After; 409 past_capture / has_audio → re-bootstrap
  recordingId, token = resp; nextSegmentIndex = max(resp.nextSegmentIndex, highestDrainedSegment + 1); putMeta (new token); acquire the Web Lock
  if a tail is still pending (drain was blocked by stale_token) → drainTail(token)
chooseResume(): phase → preflight (mic picker, 'Resume recording'); the Resume click calls takeover() (unless one already happened this session) and then start() with the new token + nextSegmentIndex
visibilitychange → hidden while recording: run.requestData() so the current partial slice reaches IDB through the normal ondataavailable path (shrinks the usual loss toward 0 when a backgrounded tab is killed). Never do network or IDB work in pagehide/beforeunload; never use fetch keepalive or sendBeacon for parts, close or finalize (64 KiB body cap).
chooseFinalize(): finalizeRecording(recordingId, { force:true }) after the confirm when the card was 'live-elsewhere'; else no force needed (interrupted)
chooseDiscard(): discardRecording(recordingId, force when live-elsewhere) → store.deleteRecording → redirectTo `/sessions/${sessionId}`
dispose(): only from finalized / discarded / taken-over cleanup and registry eviction. NEVER from a React unmount.
```

Wake lock: best-effort `acquireWakeLock()` = `if (!('wakeLock' in navigator)) return null; try { return await navigator.wakeLock.request('screen') } catch { return null }` at start; re-acquire on `visibilitychange` → visible and on the sentinel's `release` event while capturing; `wakeLockActive` shown as a hint when false. `lib.dom` (TS 5.9) types `navigator.wakeLock` as always present, so TypeScript will NOT force this guard — write it anyway, and never redeclare `Navigator`, `MediaRecorder` or `BlobEvent` (they exist in lib.dom and redeclaring fails `tsc`). Vitest: a `navigator` without `wakeLock` still reaches `recording`.

`src/components/recording/`:
- `use-recorder-engine.ts`: `engine = useMemo(() => getRecorderEngine(sessionId))`; `snapshot = useSyncExternalStore(engine.subscribe, engine.getSnapshot, getIdleServerSnapshot)` (constant frozen idle object for SSR — `'use client'` pages are still server-rendered). No effect here starts anything; effect cleanups only unsubscribe.

## Pitfalls checklist (each verified against this repo; the implementer must not regress these)

**MediaRecorder / streaming**
- Only the first blob of a MediaRecorder run carries the WebM/EBML header; a segment must be exactly one run, assembled by byte-concatenation in `seq` order. An out-of-order or header-less segment does NOT fail finalize — `probeAudioDurationSeconds` never throws, single-segment finalize skips ffmpeg, so a corrupt file reaches the paid transcription step and the parts are already deleted. Ordering is load-bearing.
- `stop()` emits its final `dataavailable` asynchronously, then `onstop`; `requestData()`/`stop()` right after a timeslice boundary can yield a 0-byte blob → drop `size === 0` before IDB/upload (server 400s and close needs `partCount ≥ 1`).
- Device unplug ends the track and auto-stops the recorder (final blob still fires) → treat as mic-lost, not as Stop; never auto-finalize.
- `enumerateDevices` labels/ids are empty before the first grant. Build the AudioContext after `getUserMedia` resolves; capturing pages are exempt from the autoplay gate.
- Capture routes check the token and status at entry, then write — a takeover can commit in between. Step 1c's in-transaction `assertCapturing` and the lock-before-read takeover order are what make token rotation airtight.
- Wall-clock chunk durations are approximate; the HUD truncates to seconds; the recovery card uses the server's byte estimate.

**IndexedDB / crash recovery**
- Transactions auto-commit at a task boundary with no pending IDB request: never `await` a `fetch`, backoff sleep or anything non-IDB inside a transaction; one short transaction per op; `txDone` rejects on `abort` too (`QuotaExceededError` surfaces as an abort); a failed write must be visible (`degraded`), never swallowed. Storing the Blob directly removes the only await on the write path.
- `seq` assigned synchronously as the first statement of `ondataavailable`; part → chunk assignment persisted before the PUT starts; never renumber existing rows on recovery (`nextPartIndex` = max persisted + 1). Never order by `BlobEvent.timecode`.
- Delete a part's rows only on 2xx; never when merely queued, and never on `segment_closed`. Purge a recording's rows on finalized / discarded / 404 (matching `userId` only — 404 is ownership-masked, don't delete another account's tail on a shared browser); 30-day TTL GC on record-page mount.
- Drain order: drain with the token persisted in IDB; never take over just to drain (it rotates the token and would kill a recorder live on another device). `stale_token` mid-drain → show live-elsewhere and let the user decide. `interrupted` from the GET is drainable; `finalizing|finalized|failed` or 404 are not — surface "N s could not be attached" and delete. The leftover rows of a mid-segment tail lack the WebM header, so do not offer them as a download.
- Two tabs in the same browser share one IDB and the engine registry is per JS context: the live recorder holds a Web Lock `recorder:<recordingId>`; a second tab that finds it held must not drain or PUT.
- The IndexedDB capability probe must actually open, write, read and delete with a timeout; `typeof indexedDB` is not enough. Firefox with storage blocked throws from the `window.indexedDB` getter itself.
- Firefox's "delete site data on close" wipes the un-uploaded tail at browser shutdown; the drain cannot recover it there. Document, don't engineer around it.
- Chrome's default IDB durability is relaxed (no fsync): `{ durability: 'strict' }` on readwrite transactions is harmless where unsupported.

**Races / concurrency**
- Never start `getUserMedia` / `MediaRecorder` / `POST /recording` from an effect: React StrictMode is on (no `reactStrictMode` override in `next.config.ts`), effects double-run in dev, Fast Refresh re-runs effects and keeps the old engine instance alive (document: editing engine modules in dev needs a full reload).
- All capture-endpoint 409s are terminal for that tab except `parts_missing`/`segment_closed` (the latter only for that part, which stays unresolved); only network / 5xx / 429 retry. Never treat every 409 as "taken over" (finalize/discard 409 for other reasons).
- Stop: await `onstop` → flush → drain → close → finalize; keep heartbeats through the drain; bump the generation before the finalize POST so a late 409 `not_capturing` from a pre-Stop heartbeat is ignored.
- Rotation only from `recording`; deferred while paused; Stop sets `stopRequested` before joining the chain so "rotate then stop" cannot spawn an empty segment. Never open segment N+1 parts before its `open` job; the next index is `last opened + 1` client-side (the server returns `nextSegmentIndex` only on start/takeover) and must never skip an index even if a segment ends up empty.
- After `finalized`, the session is briefly `uploaded` with the completed finalize job as `/progress.job` (`getLatestJob` returns any type) — hence the `job.type` addition and the 5 s grace; `uploaded` with no job is legitimate for test accounts without `MOCK_AI_SERVICES`.
- `POST /recording` is 10/min in prod and shares its bucket with billing checkout; 429 must render "Please wait N s", never "unsupported browser".
- `DELETE /api/sessions/[id]` cascades rows but not part objects; a live tab then gets 404 → terminal.

**React / Next / styling**
- `useSearchParams` needs a `<Suspense>` boundary; pages self-guard auth; `useSyncExternalStore` needs a stable snapshot and a server snapshot; `--sp-*` tokens require `useSessionTheme()`; ESLint `no-explicit-any` and unused vars fail `next build`; lucide icons to use: `Mic`, `MicOff`, `Pause`, `Play`, `Square`, `AlertTriangle`, `WifiOff`, `Loader2`, `RefreshCw` (verify against `node_modules/lucide-react/dist/lucide-react.d.ts`).

## Implementation notes (2026-09-23)

Built on `feat/live-recording-ui`. Where the implementation deliberately departs from the text above:

- **Assembler sealing is synchronous.** The Step 3 pseudo-code stamps `partIndex` synchronously but calls `assembler.add` inside the async write chain; a chunk arriving while the sealing chunk was still queued would be stamped with the already-sealed part. `onChunk` now assigns seq, stamps, AND adds/seals synchronously; only enqueueing the sealed part waits for its chunks' IndexedDB writes.
- **The pre-flight hook owns the stream**, so a fresh start goes `idle → starting` (added to the phase table) and `start({ stream, ... })` receives the stream; the engine's `preflight` phase is only used for Resume / Take over.
- **`onPartAcked` fires after the job leaves the queue**, so `pendingParts` (and "All audio saved through …") reflect the true backlog.
- **`bootstrapped` snapshot flag** distinguishes "still deciding" from "fresh session → pre-flight" (both are phase `idle`).
- **Resume after a successful stored-token drain takes over with `force`**: the drain's PUTs refreshed the heartbeat (so a plain takeover would 409 `still_capturing`), and the accepted stored token proved this browser owns the recording.
- **`ffprobeBinary()`**: `ffprobe-static`'s path is bogus under the Turbopack dev server (and CI), so every probe failed silently; probes now fall back to the system `ffprobe`.

### Review fixes (PR #50, 2026-09-23)

- **Takeover vs finalize:** takeover now locks the RECORDING row (`SELECT … FOR UPDATE`) and re-reads its status before deciding, and its token rotation is a conditional `updateMany` on `status IN ('recording','paused')`. The session-row lock alone didn't serialize with `beginFinalize` (a single UPDATE on the recording row that never takes the session lock). Verified against Postgres: 150 concurrent takeover/finalize races went from 18 "both succeeded, status flipped back to recording" to 0.
- **Part objects:** every upload attempt writes its own immutable key (`recording/<user>/<rec>/<seg>/<part>-<attempt>.part`) and publishes it only inside the guarded transaction; a rejected attempt deletes only its own object and a replaced object is deleted only after the new reference commits. A stale tab's cleanup can no longer delete an object a concurrent accepted upload wrote (50/50 concurrent stale+accepted races: 0 missing ledger objects, 0 orphans).
- **Stop joins every recorder stop:** rotation, mic-loss and long-pause stops are tracked; Stop awaits all of them before draining and finalizing. A timeout is NOT a completed stop: after 15 s the snapshot flags `stopStalled` and the HUD offers "Finalize without it" behind a confirm, but Stop keeps waiting — only that explicit choice (`abandonStalledStop()`) moves on, finishing the stalled segments with the audio that did arrive and dropping anything later.
- **Refused parts are never silently skipped** (see the error policy and `tail-blocked` above).
- **Oversized blobs are split** into bounded parts (see above).
- **Synchronous IndexedDB throws** (`putChunk` constructing the transaction on a closed connection) fall back to memory like rejections.
- **Orphaned `finalizing`:** bootstrap re-POSTs finalize (idempotent; the server re-enqueues when no job is active) instead of polling forever.
- **Unload guard survives navigation:** `<RecordingUnloadGuard/>` in the Navbar asks the registry at `beforeunload` time, so a reload/close on any page is guarded while an engine captures, uploads, or is blocked.
- **Mic switch after Stop:** `selectDevice` re-checks a capture generation after each await and stops a late-acquired stream instead of attaching it to a stopped engine.
- **Session-page finalize** recovers this browser's local tail first (see the recovery card above).
